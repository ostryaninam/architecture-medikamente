Аудит безопасности данных в компании «Медикаменте»

На текущий момент все процессы компании работают с конфиденциальными данными без достаточной защиты. 
Доступ к данным имеют все сотрудники, отсутствует разграничение ролей, средства защиты и мониторинга.

Проблемные зоны:

1. Хранение данных в файловой системе (Excel, сканы)
- Данные доступны всем сотрудникам, отсутствует централизованное управление доступом.
– Невозможно настроить гибкие политики безопасности.

2. Только доменная авторизация
– Нет разграничения доступа на уровне приложений.
– Нет поддержки RBAC или ABAC.

3. Ручной ввод данных без валидации
– Высокий риск ошибок, искажения информации и отсутствия консистентности.

4. Отсутствие мониторинга и аудита действий
– Действия пользователей не отслеживаются.
– Нельзя отследить инциденты доступа или утечек.

5. Нет защищённых каналов передачи данных
– Возможность перехвата данных в пути (например, при передаче сканов по e-mail или в сети).

6. Отсутствие разграничения доступа по ролям
– Любой сотрудник может просматривать или редактировать чувствительные данные, включая медицинские карты и финансовую информацию.

7. Отсутствие классификации и тегирования данных
– Нет деления данных на уровни чувствительности: ПДн, мед.тайна, фин. данные и т.д.
– Сложно применять избирательные меры защиты.

8. Нет шифрования данных
– Данные хранятся и передаются в открытом виде.

9. Нет механизма удаления данных по запросу
– Нарушение требований законодательства (например, 152-ФЗ).



Предложения по улучшению

1. Список данных и способы защиты:

Персональные данные (ФИО, телефон, адрес, e-mail):
Защита: шифрование при хранении и передаче.

Медицинские данные (диагнозы, жалобы, история болезни):
Защита: шифрование, разграничение доступа, аудит.

Платежные данные (сумма, способ оплаты, чек):
Защита: обфускация - токенизация.

Результаты анализов:
Защита: обезличивание, аудит, разграничение доступа.

Учётные записи пользователей (логины, действия):
Защита: аудит, контроль доступа по ролям.

2. Система тегирования данных:

PII: ФИО, адрес, телефон, e-mail
PHI: диагнозы, жалобы, назначения
Клинические данные: результаты анализов
Платежные данные: чек, сумма, реквизиты
Идентификаторы: ID пациента, номер карты, UUID
Служебные: журналы доступа, тех. статусы

Дополнительные теги для источников данных:

lab_results: данные из лабораторий
patient_input: данные, введённые вручную
external_partner: данные из внешних API

3. Механизмы управления доступом по тегам:

Настроить доступ к тегам на основе ролей (RBAC/ABAC):
Ресепшен — доступ к PII
Врачи — доступ к PII, PHI, Клинические данные
Бухгалтерия — доступ к Платежным данным, PII

Удаление данных:
PII — по запросу клиента
Клинические данные — по сроку хранения

Аудит:
Все действия с PHI и Клиническими данными должны логироваться

Маскирование:
Применять в отчётах и аналитике для скрытия ПДн

4. Инструменты и решения:

Платформы для классификации и управления данными
У компании есть два варианта:

1) Взять только Informatica.
Это универсальная платформа, которая закроет каталог, lineage, теги, роли и интеграции для BI/ML. 
Приватность персональных данных реализуется через теги и политики доступа, а также может усиливаться средствами DLP, IAM и API-шлюзом.
Плюсы: проще сопровождать одну систему.
Минусы: меньше возможностей «из коробки» по privacy и комплаенсу.

2) Взять две платформы: BigID + Informatica (или Atlas).
BigID отвечает за обнаружение и защиту персональных данных, DSAR и автоматизацию приватности, а Informatica — за каталогизацию, BI, lineage и аналитику.
Плюсы: каждая часть задачи закрыта полностью.
Минусы: дороже и сложнее в сопровождении.

Для аудита можно использовать Victoria Metrics или ELK.

5. Защита каналов передачи данных:

Все API и веб-интерфейсы должны использовать HTTPS с TLS 1.2 или выше
Внутренние соединения между сервисами — через mTLS
Передача данных между филиалами — через VPN или Zero Trust
Шифрование e-mail с результатами анализов — S/MIME или PGP

6. Использование безопасной реляционной СУБД:

Текущая архитектура не предусматривает централизованное хранение данных в промышленной СУБД.
Для обеспечения безопасности, масштабируемости и контроля доступа необходимо внедрить защищённую базу данных, например, PostgreSQL с включённым:

Шифрованием данных на уровне хранения (TDE или шифрование отдельных колонок),
Контролем доступа по ролям (RBAC),
Журналированием операций (audit logs),
Поддержкой TLS для защищённого соединения.

Также требуется миграция текущих Excel-файлов и сканов в эту СУБД (или, при необходимости, в безопасное файловое хранилище с разграничением доступа).
